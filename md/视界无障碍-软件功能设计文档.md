> V0.6.0 现行增量：在线执行路径与原静态沙箱分离；Playwright、HTTP 检查器、ZAP 与 k6 共用登记范围，重型任务由单线程执行器串行调度。Flyway V5–V7 增量保存统一运行、协作回归和报告快照。详见《视界-V0.6.0-实施与验收.md》。

## V0.5.0 现行增量设计

Flyway V4 新增 `report_snapshots`，保存扫描关联、幂等键、原始 JSON 正文、SHA-256、生成时间及 PDF/JSON 工件引用。创建事务使用 REPEATABLE_READ，并先锁定所属扫描行，使同扫描并发幂等请求串行；正文与扫描统计、复核记录在同一读取视图内冻结。后续导出只读取快照，失败不改变正文。

新增接口：

- `GET /api/projects/{projectId}/demo-state?versionId=&scanId=`：校验项目/版本/扫描归属，派生步骤状态和补丁复测入口。
- `GET /api/projects/{projectId}/comparison?beforeScanId=&afterScanId=`：返回可比性、原因、逐条配对、分类统计、证据、DOM 摘要及补丁。
- `POST /api/scans/{scanId}/report-snapshots`：要求 Idempotency-Key；同一扫描和键唯一，返回快照封装。
- `GET /api/scans/{scanId}/report-snapshots`：历史快照列表及已生成格式。
- `GET /api/report-snapshots/{snapshotId}` 与 `/export?format=pdf|json`：读取和导出固定快照。

快照封装为 `{snapshotId, contentHash, generatedAt, report}`。正文哈希基于数据库原始 JSON 字符串 UTF-8 字节，不基于下载格式化后的 JSON 文件。旧报告接口桥接最新快照并通过响应头 X-Report-Snapshot-Id 返回标识；已有工件不改写。

扫描配置新增 resolvedPages 保存实际成功页；历史扫描没有明确范围时不可进行改善计数。问题按规则/页面/标准化选择器匹配，证据指纹仅用于标记证据变化。所有状态含已驳回结果参与配对，防止将人工结论变化当作修复。确认目标修复还要求补丁记录的 rescanId 与对比复测相同。

运行脚本记录项目根目录、JAR、PID、启动时间和端口。停止前匹配进程命令行及创建时间，不停止未登记进程；MySQL 使用 compose stop 保留卷。本节覆盖以下历史报告导出设计。

## 1. 文档目的与范围

本文档将已定稿的产品需求转换为可实现的软件设计，定义系统模块、数据模型、关键流程、接口契约、安全边界和测试策略。它是前后端开发、规则实现、联调和验收的共同依据。

### 1.1 实现边界

当前 V0.4.0 在 P0 与 R001/R003 AI 候选修复闭环上，新增 R007 页面级正反向焦点轨迹、R009 阅读顺序启发式候选、可视化证据、AI 辅助解释、人工复核及项目级精确结论复用。R009 始终由本地算法生成，AI 不改变结论且不能生成补丁；没有 AI 服务和外网时全部扫描与复核功能仍可运行。

### 1.2 设计原则

1. **规则优先**：确定性问题由可重复的规则引擎判断，AI 不改变规则结果。
2. **证据优先**：每条问题均可追溯到页面、元素、代码位置、截图区域或键盘操作记录。
3. **版本不可变**：上传的原始项目和每个修复版本均只读保存，修复永远生成新版本。
4. **最小修改**：补丁只编辑与问题直接相关的源文件片段，所有应用前修改都展示 Diff。
5. **默认隔离**：不执行上传项目的构建或系统命令；浏览器默认禁止访问网络、宿主机资源和下载能力。
6. **可降级**：AI、截图标注或单条规则失败不能使已完成的基础扫描结果丢失。

### 3.2 页面交互约定

1. 所有可能改变版本的操作均展示二次确认和影响范围。
2. 扫描进度通过 SSE 实时推送；连接失败时退化为每 3 秒轮询任务详情。
3. 问题详情中的截图、代码和文字说明使用同一个 `findingId` 加载，避免展示不同扫描版本的证据。
4. AI 提示统一展示“AI 建议”标识及置信度等级；“需要人工复核”不可显示为已确认问题。
5. 评分区域固定展示“内部风险分，不是 WCAG 合规评分”。

### 3.3 前端状态模型

| 状态 | 来源 | 处理方式 |
|---|---|---|
| 页面数据 | REST 查询 | 由 TanStack Query 缓存、失效与重试 |
| 扫描进度 | SSE / 轮询 | 以服务端 `progress`、`stage`、`status` 为准 |
| 筛选条件 | URL Query 参数 | 支持分享和刷新后恢复 |

### 4.2 异步任务模型

扫描属于长耗时任务，HTTP 请求只负责创建任务：

1. `POST /scans` 在事务内创建 `scan_task`，状态为 `PENDING`。
2. 事务提交后，调度器将任务提交到单线程 `ThreadPoolTaskExecutor`。
3. 执行器按阶段更新任务状态、进度、日志和已发现问题数，并发布 SSE 事件。
4. 执行结束后统一写入 `COMPLETED`、`PARTIAL`、`FAILED` 或 `CANCELLED`。
5. 应用启动时将遗留的 `RUNNING` 任务标记为 `FAILED`，错误原因标为“服务重启导致任务中断”；用户可重新扫描。

MVP 的扫描并发数固定为 1，避免多个 Chromium 同时运行造成现场演示不稳定。后续需要并发时，再引入独立扫描器和消息队列。

### 4.3 扫描任务状态机

```text
PENDING → RUNNING → COMPLETED
                  ├→ PARTIAL
                  ├→ FAILED
                  └→ CANCELLED

PENDING / FAILED / PARTIAL / CANCELLED → PENDING（重新扫描时创建新任务）
```

任务阶段为：`FILE_CHECK`、`PAGE_START`、`DOM_ANALYSIS`、`CSS_ANALYSIS`、`RULE_CHECK`、`SCREENSHOT`、`KEYBOARD_TEST`、`AI_ANALYSIS`、`AGGREGATION`、`SCORING`。

## 5. 数据库与文件存储设计

### 5.1 设计约定

- 数据库使用 MySQL、InnoDB、`utf8mb4` 字符集和 `utf8mb4_0900_ai_ci` 排序规则。
- 主键使用 `CHAR(26)` 的 ULID，便于按创建时间排序且对外暴露安全。
- 时间字段使用 `DATETIME(3)`，统一以 UTC 写入、前端按本地时区展示。
- 可变结构化证据使用 `JSON` 类型；需要筛选的核心字段必须独立成列。
- 源码、截图、PDF 和大体积 JSON 不存入 BLOB，数据库只保存路径、哈希、大小和关联关系。

### 5.2 核心表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `projects` | `id`、`name`、`description`、`type`、`current_version_id` | 项目基本信息 |
| `project_versions` | `id`、`project_id`、`base_version_id`、`version_no`、`source_type`、`storage_path`、`manifest_hash` | 原始和修复版本 |
| `stored_artifacts` | `id`、`project_id`、`version_id`、`scan_task_id`、`kind`、`relative_path`、`sha256`、`size_bytes` | ZIP、截图、日志、报告等文件元数据 |
| `scan_tasks` | `id`、`project_id`、`version_id`、`status`、`stage`、`progress`、`scan_config`、`rule_version` | 扫描任务与配置快照 |
| `scan_logs` | `id`、`scan_task_id`、`level`、`stage`、`message`、`details` | 可展示的任务日志 |
| `findings` | `id`、`scan_task_id`、`rule_id`、`source`、`severity`、`status`、`page_path`、`selector`、`fix_mode` | 问题主记录 |
| `finding_evidences` | `id`、`finding_id`、`kind`、`payload`、`artifact_id` | DOM、CSS、截图、焦点路径等证据 |
| `fix_patches` | `id`、`finding_id`、`base_version_id`、`new_version_id`、`patch_type`、`candidate_text`、`decorative`、`source_evidence_id`、`source_provider`、`source_model`、`reviewed_at`、`diff_text`、`status`、`verification` | 模板/AI 候选修复、来源与审核结果 |
| `finding_reviews` | `id`、`finding_id`、`action`、`comment`、`created_at` | 确认、忽略和人工复核记录 |
| `report_exports` | `id`、`scan_task_id`、`format`、`artifact_id`、`status` | PDF/JSON 导出记录 |

### 5.3 关键索引与约束

| 表 | 约束或索引 | 目的 |
|---|---|---|
| `project_versions` | `UNIQUE(project_id, version_no)` | 一个项目的版本号唯一 |
| `scan_tasks` | `INDEX(version_id, created_at)` | 按版本查看扫描历史 |
| `findings` | `INDEX(scan_task_id, severity, status)` | 问题列表筛选与排序 |
| `findings` | `INDEX(scan_task_id, rule_id, page_path)` | 规则和页面维度统计 |
| `finding_evidences` | `INDEX(finding_id, kind)` | 问题详情快速加载 |
| `fix_patches` | `UNIQUE(finding_id, base_version_id, status)`（按业务校验） | 避免同一问题产生重复待确认补丁 |
| 全部关联表 | 外键或应用层完整性校验 | 禁止产生孤立扫描、问题和补丁 |

## 6. 项目导入、预览与安全设计

### 6.1 上传与安全解压流程

```text
接收 ZIP/HTML
  → 校验扩展名、MIME、20 MB 上传上限
  → 读取 ZIP 目录而不直接解压
  → 校验文件数量、总解压大小、单文件大小、路径与链接属性
  → 解压至临时目录
  → 校验 HTML 入口和资源白名单
  → 生成文件清单与 SHA-256
  → 原子移动到版本目录
  → 创建原始 project_version
```

校验规则：

- 拒绝绝对路径、空路径、`..`、Windows 盘符、UNC 路径和符号链接；
- 拒绝嵌套压缩包、可执行文件、`.bat`、`.cmd`、`.exe`、`.ps1`、`.jar`、`.py` 等非网页资源；
- 只允许 HTML、CSS、JS、JSON、SVG、图片、字体和必要文本资源；
- 限制为 500 个文件、100 MB 解压总量，并设置单文件上限；
- 不执行 `npm install`、构建脚本、shell、Node、Python 或用户提供的其他命令；
- 任一校验失败时删除临时目录，不创建项目版本。

### 6.2 受限预览与扫描上下文

浏览器不能直接用 `file://` 或可访问的 `localhost` 静态服务器加载上传项目。扫描器为每个任务创建一次性 Chromium Context，并按以下方式运行：

1. 启用虚拟项目 Origin，例如 `http://project.local/`；
2. 使用 Playwright `route` 拦截所有页面请求，仅从当前版本受控目录读取白名单资源并 `fulfill`；
3. 对外网、局域网、回环地址、WebSocket 和非项目路径请求一律 `abort`；
4. 禁用 Service Worker、下载、权限请求和持久化 Cookie；
5. 设置页面加载、单个脚本行为和整页扫描的超时；
6. 每页扫描完成后关闭 Page 和 Context，不复用用户项目的运行状态。

JavaScript 可在页面中执行以还原静态网页的真实渲染效果，但不具有访问宿主机文件、环境变量或网络的能力。生产部署应将扫描器放入非 root、无网络、受 CPU/内存/PID 限制的容器；本地比赛模式仍需保留上述浏览器与文件限制。

## 7. 扫描与规则引擎设计

### 7.1 扫描流水线

```text
加载版本和配置
  → 文件完整性校验
  → 创建受限浏览器上下文
  → 逐页渲染并采集 DOM、计算样式、元素坐标
  → 执行 R001–R006、R008
  → 截图与问题区域裁剪
  → 执行 R007 键盘焦点路径测试
  → 运行 axe-core 并去重映射为辅助证据
  → 可选 AI 语义分析
  → 聚合问题、保存证据、计算风险分
  → 关闭浏览器并完成任务
```

每个页面发生异常时，记录该页失败原因并继续处理其他页面；最终任务标记为 `PARTIAL`。浏览器无法启动、版本目录缺失等全局异常才标记为 `FAILED`。

### 7.2 统一规则接口

```java
public interface AccessibilityRule {
    String ruleId();
    RuleResult evaluate(PageSnapshot snapshot, RuleContext context);
}
```

`PageSnapshot` 是一次渲染的不可变快照，包含页面路径、DOM 摘要、元素属性、计算样式、坐标、HTML 源码映射和截图引用。规则不得自行重新加载页面，也不得修改页面源码。

### 7.3 P0 规则设计

| 规则 | 判断逻辑 | 主要证据 | 默认修复模式 |
|---|---|---|---|
| R001 图片缺少 alt | 检查有效 `img` 是否缺少 `alt` 属性；空 alt 不判定为失败，只进入 P1 AI 提示 | 元素 HTML、选择器、截图区域 | 候选建议 |
| R002 表单控件缺少名称 | 对可输入控件检查 `label[for]`、祖先 `label`、`aria-label`、`aria-labelledby` 等关联 | 控件与标签片段、关联计算结果 | 已有可见标签时模板补丁，否则建议 |
| R003 按钮/链接缺少名称 | 检查文字、`aria-label`、`aria-labelledby`、图片 alt 等可访问名称来源 | 元素 HTML、名称来源 | 候选建议 |
| R004 页面语言缺失 | 检查根 `html` 是否含合法非空 `lang` | 根标签源码位置 | 模板补丁，需用户确认语言 |
| R005 标题层级风险 | 提取可见 H1–H6，检查缺 H1 和跳级；仅作为建议 | 标题序列、DOM 位置 | 仅提示 |
| R006 纯色文字对比度不足 | 读取计算前景/背景色，仅对可确定的纯色进行 WCAG 对比计算；渐变、背景图、透明叠层标人工复核 | 色值、对比度、截图 | 候选 CSS 建议 |
| R007 键盘焦点风险 | 固定路径 Tab/Shift+Tab，记录焦点顺序、焦点矩形与可见样式；只描述已执行路径 | 焦点轨迹、元素坐标、截图 | 缺失焦点样式时模板建议 |
| R008 ID/ARIA 引用异常 | 建立 ID 索引，检测重复 ID 和 `aria-labelledby`、`aria-describedby` 等失效引用 | 引用属性、目标列表、源码位置 | 仅提示 |

### 7.4 严重程度与去重

严重程度由规则和页面上下文确定，不使用 AI 置信度计算：

- 高：R001、R002、R003、R007 中明确阻断使用的情形；
- 中：明确降低操作或理解效率的情形；
- 低：标题层级、可改善的焦点表现等建议类问题。

相同 `scanTaskId + ruleId + pagePath + normalizedSelector` 的规则结果只能保留一条。axe-core 输出只作为同一 Finding 的补充证据或 P1 扩展提示，不生成与产品规则重复的 P0 Finding。

### 7.5 证据模型

```json
{
  "kind": "dom|css|screenshot|keyboard|axe|ai",
  "summary": "输入框未关联可见标签",
  "selector": "#email",
  "sourceRange": { "file": "index.html", "start": 241, "end": 278 },
  "boundingBox": { "x": 112, "y": 316, "width": 320, "height": 40 },
  "artifactId": "01J...",
  "details": {}
}
```

## 8. AI 语义分析设计（P1）

### 8.1 调用时机与输入最小化

AI 仅在用户启用、完成外部服务告知并确认后执行。触发对象为基础规则已命中的图片、按钮、链接、标题、表单提示和阅读顺序风险。

每次请求最多包含：问题元素截图、元素 HTML、有限 DOM 上下文、关联 CSS、元素周边可见文本、对应规则结果。不得发送整个 ZIP、全部页面源码、数据库记录、密钥、Cookie 或宿主机路径。

### 8.2 `AiProvider` 接口

```java
public interface AiProvider {
    AiAnalysisResult analyze(AiAnalysisRequest request);
}
```

所有 Provider 返回结果均在服务端进行 JSON Schema 与业务校验；不合格响应标记为 `AI_ANALYSIS_FAILED`，不影响基础扫描与报告导出。

### 8.3 结构化响应契约

```json
{
  "conclusion": "建议为图片补充描述性替代文本",
  "confidenceBand": "medium",
  "evidence": ["图片展示校园图书馆入口", "周边标题为‘图书馆服务’"],
  "recommendedAction": "候选 alt：校园图书馆正门",
  "reviewRequired": true,
  "candidatePatch": null
}
```

`confidenceBand` 只允许 `high`、`medium`、`low`、`manual_review`。低置信度和无法判定结果必须设置 `reviewRequired: true`，不得计入内部风险分，也不得自动应用补丁。

## 9. 修复、版本与复测设计

### 9.1 补丁类型

| 类型 | 示例 | 生成方式 | 应用条件 |
|---|---|---|---|
| P0 模板补丁 | 补 `html lang`、关联已有标签、补充焦点样式 | 确定性模板 | Diff、语法校验和用户确认均通过 |
| P1 候选补丁 | R001 图片 alt、R003 按钮/链接名称 | 已保存的 AI 证据 + 用户编辑文本 + 确定性属性补丁器 | 高/中置信度、精确源码定位、Diff 和人工确认均通过 |
| 仅提示 | 标题层级、复杂 ARIA、阅读顺序、键盘行为 | 文字建议 | 不生成可应用补丁 |

### 9.2 补丁生成流程

```text
选择 Finding
  → 加载 baseVersion 源码和证据
  → 根据 fixMode 读取模板参数或已保存的 AI 证据与用户编辑文本
  → 校验可修改文件白名单、源位置和补丁大小
  → 在临时副本应用补丁
  → HTML/CSS 基础语法校验
  → 生成统一 Diff 与影响文件清单
  → 保存 FixPatch（PENDING）
```

V0.4.0 保留的 AI 候选补丁只修改一个 HTML 文件中的一个目标开始标签：R001 插入 `alt`，R003 插入 `aria-label`。候选文本先压缩空白、过滤控制字符并进行 HTML 属性转义。动态生成元素、选择器不唯一、源码已有目标属性或位置无法确认时拒绝生成；不得猜测修改、删除文件、增加网络 URL 或脚本。R009 不进入该补丁流程。

### 9.3 应用、回滚与复测

1. 用户确认后，在 `baseVersion` 的完整文件副本上应用补丁，生成新的 `project_version`。
2. 保存新版本清单哈希和 `FixPatch.new_version_id`，原始版本不写入。
3. 创建复测任务，并复制原扫描的页面集合、规则和键盘测试配置；强制关闭 AI，不进行二次语义分析。
4. 复测结束后对比同一规则、页面和标准化选择器。原问题消失时为 `VERIFIED`，仍存在时为 `FAILED`；任务失败、取消或部分完成时保持 `APPLIED` 并允许重新扫描。
5. 回滚不删除任何版本，仅将项目当前展示版本切换为补丁的基准版本，并保留操作记录。

AI 补丁的 `verification` 至少保存 `ruleCleared`、`validationLevel: "RULE"`、`semanticReview: "HUMAN_ACCEPTED"`、`aiReanalysis: false` 和 `retestStatus`。这只证明基础规则复测结果，语义正确性由确认用户负责。

### 9.4 补丁状态机

```text
PENDING → APPLIED → VERIFIED
    ├── REJECTED
    ├── INVALID
    └── ROLLED_BACK（仅已应用版本可进入）
```

## 10. 内部风险分与报告设计

### 10.1 评分服务

评分只读取已确认的基础规则 Finding：

```text
内部风险分 = max(0, 100 - 10 × 高风险问题数 - 4 × 中风险问题数 - 低风险问题数)
```

评分记录必须保存公式版本、规则版本、扫描配置、统计时刻和扫描任务 ID。AI 提示在人工确认前不参与计算。

### 10.2 报告生成

报告服务按固定数据快照生成 HTML，再使用受控 Chromium 导出 PDF。报告页必须使用内置中文字体并包含：

1. 项目和版本概况；
2. 扫描范围、时间、规则版本和运行环境；
3. 内部风险分及计算口径；
4. 问题统计、高风险问题详情、截图和代码位置；
5. AI 分析执行状态和人工复核事项；
6. 修复记录、前后对比、复测结论和新增问题；
7. 免责声明：仅覆盖已启用规则和已扫描页面，不构成完整无障碍合规结论。

JSON 导出使用与页面相同的 `scanTaskId` 数据快照，避免报告与页面统计不一致。

## 11. 接口设计

### 11.1 通用约定

- 所有 API 前缀为 `/api`，请求和响应使用 JSON；文件上传使用 `multipart/form-data`。
- ID 使用 ULID 字符串。
- 成功响应返回业务数据；错误响应统一为 `{ "code", "message", "traceId", "details" }`。
- 删除、应用修复、回滚等写操作需要 `Idempotency-Key`，避免用户重复点击产生重复版本。

### 11.2 核心接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/projects` | 创建项目 |
| `GET` | `/api/projects` | 项目列表 |
| `POST` | `/api/projects/{projectId}/upload` | 上传 ZIP/HTML 并生成原始版本 |
| `GET` | `/api/projects/{projectId}/files` | 获取目录树与入口页 |
| `POST` | `/api/projects/{projectId}/scans` | 创建扫描任务 |
| `GET` | `/api/scans/{scanId}` | 查询扫描状态和统计 |
| `GET` | `/api/scans/{scanId}/events` | SSE 扫描进度流 |
| `GET` | `/api/scans/{scanId}/findings` | 分页查询问题列表 |
| `GET` | `/api/findings/{findingId}` | 查询问题、证据与修复状态 |
| `POST` | `/api/findings/{findingId}/fix-patches` | 生成补丁或候选建议 |
| `POST` | `/api/fix-patches/{patchId}/apply` | 确认应用补丁并创建复测 |
| `POST` | `/api/fix-patches/{patchId}/reject` | 拒绝补丁 |
| `POST` | `/api/versions/{versionId}/rescan` | 以指定配置重新扫描 |
| `POST` | `/api/versions/{versionId}/rollback` | 切换当前展示版本 |
| `GET` | `/api/scans/{scanId}/report?format=pdf|json` | 导出报告 |

AI 候选补丁生成请求为 `{ "aiEvidenceId", "candidateText", "decorative" }`；模板补丁继续接受 `{ "language" }`。AI 补丁应用请求必须包含 `{ "reviewAccepted": true }`，否则返回 `AI_REVIEW_REQUIRED`。相同待审候选请求幂等返回原补丁，不同内容返回 `PATCH_ALREADY_PENDING`。

## 12. 安全、可靠性与可观测性

### 12.1 安全控制清单

| 风险 | 控制措施 |
|---|---|
| ZIP 路径穿越与压缩炸弹 | 解压前目录检查、路径规范化、数量/大小限制、临时目录原子移动 |
| 网页访问内网或外网 | Playwright 全请求路由白名单，默认中止所有非项目资源请求 |
| 网页读取宿主机资源 | 不使用 `file://`，不暴露本地静态端口，受限目录与一次性 Context |
| 恶意下载或持久化 | 禁止下载、Service Worker、权限请求、持久化 Cookie |
| AI 泄露源码/截图 | 明示告知、用户开关、最小上下文、密钥仅存服务端环境变量 |
| 自动修复误改 | 模板白名单、补丁大小限制、Diff、用户确认、临时校验和强制复测 |
| 文件越权读取 | 所有文件访问使用项目/版本/工件关联校验，禁止直接传磁盘绝对路径 |

### 12.2 日志与错误处理

- 每个 HTTP 请求生成 `traceId`，记录在 API 日志和错误响应中。
- `scan_logs` 存储用户可见的阶段日志，服务端详细堆栈只写应用日志。
- 规则异常转化为单条规则失败证据，不中断其他规则；页面异常转化为页面失败日志，不中断其他页面。
- 外部 AI 错误区分超时、鉴权、限流、响应不合法；允许单独重新运行 AI 分析。

### 12.3 性能目标

在 10 个静态页面、默认 8 条规则、单并发扫描条件下，目标为 60 秒内完成。实现上采用页面顺序扫描、元素与截图按需采集、同页复用浏览器 Context；不在 P0 中并发启动多个 Chromium 实例。

4. 应用 `lang` 或已有标签关联补丁后生成新版本，原始版本不变，复测问题数真实下降。
5. 报告中的项目版本、问题数和风险分与扫描详情一致，中文截图可正常显示。
6. 浏览器中任意外部、局域网和回环请求均被拦截并记录为资源加载失败，不导致服务崩溃。

## 15. 开发顺序与完成标准

### 15.1 推荐开发顺序

1. 初始化 React、Spring Boot、MySQL、Flyway 和统一数据契约。
2. 完成项目 CRUD、安全上传、版本目录和预览。
3. 接入 Playwright，完成受限请求路由、截图和任务进度。
4. 实现 R001–R009、统一 Finding、页面轨迹和问题列表/详情。

7. 完成规则样例集、端到端验收和比赛演示脚本。
8. P0 稳定后再接入 AI 分析和候选修复。

### 15.2 P0 完成定义

P0 完成时，系统必须可在指定环境中独立启动，并连续完成“导入 → 扫描 → 查看证据 → 生成并确认模板补丁 → 自动复测 → 导出报告”的演示闭环。所有统计必须由真实扫描结果生成；不得将 AI 建议、内部风险分或已启用规则覆盖范围表述为完整 WCAG 合规结论。

## 16. V0.4.0 增量设计（现行基线）

### 16.1 数据与状态

Flyway V3 为 `scan_tasks` 增加 `review_count`，为 `findings` 增加 `evidence_fingerprint`；新增 `page_analysis_traces` 与 `project_review_policies`，并为 `finding_reviews` 增加 `reused`、`source_policy_id`。页面轨迹通过截图工件引用复用同一全页截图。

R009 初始状态为 `NEEDS_REVIEW`。确认后为 `CONFIRMED`，驳回后为 `DISMISSED`。复用键为项目、规则、页面、标准化选择器和证据指纹的 SHA-256；证据指纹覆盖截断源码、名称、相关计算样式、坐标与顺序。

### 16.2 扫描算法

- R007 分别从页面起点执行 Tab 与 Shift+Tab，记录最多 30 个唯一焦点目标；重复目标判定循环，达到上限标记截断。
- R009 采集最多 80 个可见语义块和交互元素，按页面方向对几何位置排序，并比较 DOM 索引。明确倒置以 16px 为阈值；少于 4 个候选、少于 2 个倒置或比例低于 0.15 时不生成候选，明确 CSS `order` 重排除外。
- 垂直或未知书写模式保存 `UNSUPPORTED` 轨迹，不生成 R009。

### 16.3 AI 隔离

R009 请求由最多 4 个冲突局部区域构成编号拼图，文本上下文最多包含 12 个截断元素摘要。响应只保存概述、置信度、理由与复核建议，`candidateText` 在适配器和持久化层均强制为空。超时、未授权和非法 JSON 只写警告，不影响离线证据。

### 16.4 统计与报告

严重度和风险分查询排除 `NEEDS_REVIEW`、`DISMISSED`；`found_count` 仅排除 `DISMISSED`，`review_count` 统计 `NEEDS_REVIEW`。报告快照同时包含页面轨迹、复核历史、复用来源和四类结论标签。
